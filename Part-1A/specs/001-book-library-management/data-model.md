# Data Model: Book Library Management System

All persisted entities use MongoDB-generated ObjectIds. Timestamps are stored in UTC
unless identified as calendar dates. User-facing identifiers and references are returned
as strings.

## Book

Represents one lendable inventory record with a unique ISBN.

| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | Generated by MongoDB. |
| `title` | string | Required, trimmed, non-empty. |
| `author` | string | Required, trimmed, non-empty. |
| `isbn` | string | Required; original display value. |
| `isbn_normalized` | string | Required; trimmed and case-folded for unique index. |
| `category` | string | Required, trimmed, non-empty. |
| `status` | enum | `available`, `issued`, or `maintenance`; defaults to `available`. |
| `created_at` | UTC datetime | Set on creation. |
| `updated_at` | UTC datetime | Updated on every change. |
| `archived_at` | UTC datetime or null | Set on deletion when historical loans exist; omitted from normal listings. |

**Indexes and invariants**

- Unique index on `isbn_normalized`.
- Indexes support status/category filtering and deterministic listing by title,
  creation date, or status priority with `_id` as tie-breaker.
- Status-priority sorting orders `available`, then `issued`, then `maintenance`;
  `_id` is the final stable tie-breaker.
- `status=issued` corresponds to one active/overdue loan. An issued book cannot be
  changed to available or maintenance while its loan is active.
- `archived_at` records a logical deletion so historical loans retain a resolvable book.

## Member

Represents a borrower record.

| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | Generated by MongoDB. |
| `name` | string | Required, trimmed, non-empty. |
| `email` | string | Required; display form. |
| `email_normalized` | string | Required; trimmed and case-folded for unique index. |
| `active_loans_count` | integer | Non-negative; maintained in the same transaction as issue/return. |
| `created_at` | UTC datetime | Set on creation. |
| `archived_at` | UTC datetime or null | Set on deletion when historical loans exist; omitted from normal listings. |

**Indexes and invariants**

- Unique index on `email_normalized`.
- Cannot be archived while an active or overdue loan exists.
- The stored active-loan count must equal the number of active/overdue loans. It is
  changed only in the associated issue/return transaction.

## Loan

Represents one issue of one book to one member. Loans are retained as history.

| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | Generated by MongoDB. |
| `book_id` | ObjectId | Required reference to a retained book record. |
| `member_id` | ObjectId | Required reference to a retained member record. |
| `issue_date` | UTC datetime | Required; set when the issue transaction succeeds. |
| `due_date` | Calendar date | Required; 14 calendar days after issue in `LIBRARY_TIME_ZONE`. |
| `return_date` | UTC datetime, optional | Absent until returned. |
| `created_at` | UTC datetime | Set with the issue. |
| `updated_at` | UTC datetime | Updated when returned. |

**Status and invariants**

- API `status` is derived: `returned` when `return_date` exists; otherwise `overdue`
  when the current library-local date is after `due_date`; otherwise `active`.
- A unique partial index on `book_id` for loans where `return_date` is absent prevents
  more than one outstanding loan for a book. Transactional conditional updates remain
  necessary for book/member consistency.
- Index `member_id, return_date` for member loan lookup and `due_date, return_date`
  for overdue lookup.
- Return is allowed exactly once for an outstanding loan; it sets `return_date`,
  changes the book to available, and decrements the member count in one transaction.

## Librarian

Authentication record required by the clarified access policy; it is not a library
member and cannot borrow books.

| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | Generated by MongoDB. |
| `email_normalized` | string | Required and unique; normalized email identifier. |
| `password_hash` | string | Required Argon2id hash; never returned by API or written to logs. |
| `created_at` | UTC datetime | Set when provisioned. |
| `disabled_at` | UTC datetime or null | Disabled accounts cannot sign in or retain valid sessions. |

No public librarian registration or role hierarchy is in scope. Provisioning is restricted
to a controlled setup operation. Development credentials are supplied through the local,
ignored `backend/.env`; `.env.example` contains placeholders only. The setup command may
create the configured librarian when absent but must not overwrite an existing account.

## Session

Server-side session storage contains an opaque session identifier, librarian reference,
CSRF secret/token state, creation and expiry timestamps. Session identifiers and CSRF
values are not exposed in logs. The browser receives only the configured secure,
HttpOnly session cookie.

## Transactional Workflows

### Issue

1. Validate identifiers and the CSRF/authentication requirements.
2. Begin a MongoDB transaction.
3. Conditionally update the book from `available` to `issued`; if it is not available,
   abort and return a client error.
4. Verify the member exists and is not archived; increment its active-loan count.
5. Create one loan with issue time and local-calendar due date.
6. Commit. Any failure aborts all writes.

### Return

1. Begin a MongoDB transaction.
2. Conditionally set the loan's `return_date` only if it is outstanding.
3. Set its book to `available` and decrement the member count without allowing a
   negative value.
4. Commit. Missing or already returned loans cause no partial updates.

Transaction callbacks use sequential database operations. Retry only transient database
transaction failures according to driver/Mongoose guidance; business conflicts are not
retried as success.

## Development Setup and Sample Records

`LIBRARIAN_EMAIL` and `LIBRARIAN_PASSWORD` are local environment configuration, not
database defaults. The password is validated and hashed with Argon2id before persistence;
it is never logged or returned. Development bootstrap requires `NODE_ENV=development`
and a loopback MongoDB host; it is unavailable in production and against remote databases.

An explicit seed command may add a small, fictional set of Book and Member records for
local testing. It uses unique normalized ISBN/email values and insert-if-absent behavior
so repeat runs do not duplicate or overwrite records. The command refuses production
mode, MongoDB URIs whose hosts are not loopback, and database names outside its
development allowlist. It is not run implicitly by the app startup script; this prevents
an environment that points at a remote Atlas cluster from being seeded accidentally.
Seed records do not create loans or alter member counts.
